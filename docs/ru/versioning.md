# Версионирование

Планируемая схема:

```txt
Generation.Major.Minor.Patch-Release
```

Коротко:

```txt
G.M.m.p-release
```

## Generation

Большая эпоха проекта.

Примеры:

- `1` - старый Sorrel Hub
- `2` - v2 / redesign era
- `3` - предыдущая NextGen era

Generation не нужно менять ради каждого redesign. Это должна быть новая эпоха проекта.

## Перезапуск 2026-06-16

После `2026-06-16 16:00 UTC+5` версии Sorrel Hub начинаются заново как новая линейка.

Нельзя смешивать версии предыдущей NextGen-эпохи с версиями после этого перезапуска. Старые версии остаются историческими и могут упоминаться как старые версии NextGen-этапа, но они не входят в новую линейку Sorrel Hub.

Этот документ не назначает конкретный новый номер версии, потому что в текущих документах его нет. Важное правило такое: версии после reset идут свежей последовательностью, а старые NextGen-номера остаются в предыдущей последовательности.

## Major

Крупные изменения, которые ломают совместимость или сильно меняют продукт.

Примеры:

- новая auth-система;
- новый loader protocol;
- крупное изменение архитектуры;
- отказ от старого API контракта.

## Minor

Новые функции без грубого ломания.

Примеры:

- Connected services;
- новая страница продукта;
- новые настройки профиля;
- новые модули.

## Patch

Фиксы, безопасность и мелкие улучшения.

Примеры:

- UI bugfix;
- CSP fix;
- loader bugfix;
- OAuth redirect fix.

## Release

Метка состояния.

Варианты:

- `dev`
- `pre-alpha`
- `alpha`
- `beta`
- `rc.1`
- `stable`
- `hotfix`

## Примеры

```txt
3.0.0.0-pre-alpha
3.1.0.0-alpha
3.1.2.0-beta
3.1.2.1-hotfix
3.2.0.0-stable
```

Это примеры старой generation-style схемы, а не назначенные версии после reset.

## Правило

Не нужно называть каждую новую кнопку `Major`.

- поменял кнопку - patch;
- добавил страницу - minor;
- поменял auth/API так, что старое поведение ломается - major;
- сменил всю эпоху продукта - generation.
